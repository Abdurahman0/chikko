# Frontend API Documentation

This document is the frontend-facing API reference for the current backend running in this repository.

Base local URL:
- `http://127.0.0.1:8000`

Main docs:
- Swagger UI: `http://127.0.0.1:8000/api/docs/`
- OpenAPI schema: `http://127.0.0.1:8000/api/schema/`

## 1. General Rules

### Authentication

Most endpoints require JWT auth.

Header format:

```http
Authorization: Bearer <access_token>
```

Auth endpoints:
- `POST /api/auth/login/`
- `POST /api/auth/refresh/`
- `GET /api/auth/me/`

### Response style

- List endpoints return plain arrays.
- Pagination is not enabled.
- UUID fields are returned as strings.
- Decimal fields are returned as strings.
- DateTime fields are returned as ISO datetime strings.
- `JSONField` values are returned as JSON objects or arrays.

### Common query params

Many list endpoints support these:
- `search=<text>`
- `ordering=<field>`
- filter params defined per endpoint

Examples:
- `GET /api/leads/?search=ali`
- `GET /api/orders/?status=waiting_payment`
- `GET /api/products/?ordering=price`

### Common error codes

- `400` validation error
- `401` missing or invalid token
- `403` authenticated but permission denied
- `404` object not found

Validation errors usually come as:

```json
{
  "field_name": ["error message"]
}
```

or

```json
{
  "detail": "error message"
}
```

## 3. Auth API

### POST `/api/auth/login/`

Login with email and password.

Request:

```json
{
  "email": "developer@example.com",
  "password": "Password123!"
}
```

Response:

```json
{
  "refresh": "jwt_refresh_token",
  "access": "jwt_access_token",
  "user": {
    "id": "uuid",
    "email": "developer@example.com",
    "full_name": "Developer User",
    "phone": "",
    "role": "developer",
    "permissions": []
  }
}
```

Fields:
- `refresh`: string
- `access`: string
- `user.id`: UUID string
- `user.email`: string
- `user.full_name`: string
- `user.phone`: string
- `user.role`: `developer | admin | operator`
- `user.permissions`: string array

Notes:
- For developer, `permissions` returns an empty array, but access is full.
- Store `access` for API calls and `refresh` for token refresh.

### POST `/api/auth/refresh/`

Request:

```json
{
  "refresh": "jwt_refresh_token"
}
```

Response:

```json
{
  "access": "new_access_token",
  "refresh": "new_refresh_token"
}
```

### GET `/api/auth/me/`

Returns the current authenticated user.

Response:

```json
{
  "id": "uuid",
  "email": "developer@example.com",
  "full_name": "Developer User",
  "phone": "",
  "role": "developer",
  "permissions": []
}
```

## 10. Payments API

Base path:
- `/api/payments/`

Permissions:
- list/retrieve: `can_view_payments`
- create/update/delete/approve/reject/verify: `can_manage_payments`

### Payment object

- `id`: UUID
- `created_at`: datetime
- `updated_at`: datetime
- `order`: UUID
- `amount`: decimal string
- `status`: `pending | approved | rejected | verified | failed`
- `method`: `manual | payme | click`
- `screenshot`: file URL or `null`
- `last_four_digits`: string
- `submitted_by_name`: string
- `reviewed_by`: UUID or `null`, read only
- `reviewed_at`: datetime or `null`, read only
- `metadata`: object
- `verification_reference`: string

### GET `/api/payments/`
### GET `/api/payments/{id}/`
### POST `/api/payments/`
### PUT `/api/payments/{id}/`
### PATCH `/api/payments/{id}/`
### DELETE `/api/payments/{id}/`

Filters:
- `status`
- `method`
- `order`

Search:
- `order__contact_name`
- `submitted_by_name`
- `last_four_digits`

Ordering:
- `created_at`
- `amount`
- `updated_at`

Create example:

```json
{
  "order": "order-uuid",
  "amount": "172000.00",
  "status": "pending",
  "method": "manual",
  "last_four_digits": "1234",
  "submitted_by_name": "Ali Valiyev",
  "metadata": {},
  "verification_reference": ""
}
```

Notes:
- `reviewed_by`, `reviewed_at`, `created_at`, `updated_at` are read only.
- Duplicate protection applies if the same `order + amount + last_four_digits` exists recently in `pending`, `approved`, or `verified`.
- For file upload, send `multipart/form-data` and include `screenshot`.

### POST `/api/payments/{id}/approve/`

Request body:
- empty body is allowed

Effect:
- payment status becomes `approved`
- order status becomes `paid`

Response:
- full updated payment object

### POST `/api/payments/{id}/reject/`

Request:

```json
{
  "reason": "Screenshot unreadable"
}
```

Effect:
- payment status becomes `rejected`
- rejection reason is stored in `metadata.rejection_reason`

Response:
- full updated payment object

### POST `/api/payments/{id}/verify/`

Request body:
- empty body is allowed

Effect:
- queues async verification job

Response:
- `202 Accepted`
- body is the current payment object

## 15. WebSocket API

WebSocket auth uses JWT in query string.

Format:

```text
ws://127.0.0.1:8000/ws/chat/<session_uuid>/?token=<access_token>
```

or

```text
ws://127.0.0.1:8000/ws/logs/?token=<access_token>
```

### Chat socket

URL:
- `/ws/chat/<session_uuid>/`

Access:
- authenticated user
- must have `can_chat`
- session must exist

Close codes:
- `4401` unauthenticated
- `4403` no permission
- `4404` chat session not found

Client send payload:

```json
{
  "content": "Operator message text"
}
```

Server sends JSON event payload generated by backend chat service.
Frontend should treat incoming payload as a new chat message event and append it to the active chat thread.

### Developer logs socket

URL:
- `/ws/logs/`

Access:
- authenticated developer only

Close codes:
- `4401` unauthenticated
- `4403` not a developer

Server sends JSON log payloads.

## 16. Frontend Implementation Notes

### Recommended auth flow

1. Login with `/api/auth/login/`
2. Save `access` and `refresh`
3. Call `/api/auth/me/`
4. Build navigation from `role` and `permissions`
5. On `401`, try `/api/auth/refresh/`
6. If refresh fails, force logout

### Recommended route gating

- `developer`: full access
- `admin`: all CRM routes except developer-only modules
- `operator`: gate per permission code

Suggested page-to-permission mapping:
- dashboard -> `can_view_dashboard`
- leads -> `can_view_leads`
- leads edit/create -> `can_manage_leads`
- customers -> `can_view_customers`
- customers edit/create -> `can_manage_customers`
- products -> `can_view_products`
- products edit/create -> `can_manage_products`
- orders -> `can_view_orders`
- orders edit/create -> `can_update_orders`
- payments -> `can_view_payments`
- payment review actions -> `can_manage_payments`
- chat -> `can_chat`
- notifications -> `can_view_notifications`
- users -> `can_manage_users`
- integrations events -> `can_manage_integrations`
- AI settings -> developer only
- logs -> developer only

### File upload note

For `Payment.screenshot`, use `multipart/form-data`.

### Decimal handling

Frontend should treat decimal values as strings for transport:
- `price`
- `unit_price`
- `line_total`
- `total_amount`
- `amount`
- `temperature`
- `order_confidence_threshold`
- `revenue`
